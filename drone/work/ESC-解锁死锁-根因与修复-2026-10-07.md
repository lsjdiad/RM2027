# 闭环起不来 —— "解锁/上锁"两处根因与修复（2026-10-07）

> 状态：**代码已改、两边都编译通过；硬件未验证（改完时电已关）。**
> 结论一句话：**电调的解锁逻辑本身没错**，卡住的是两件事——
> ① 解锁要求"油门连续约 1 秒为 0"，而测试台只在**自己复位后的前 3 秒**发 0，
>    电调每次重烧/复位都错过这个窗口；
> ② 更隐蔽：那段**必需的**零油门窗口会把 `old_routine` 钉成 1，
>    而起步那句是 `if (!old_routine) startMotor();` ⇒ **解锁过程本身把起步路径堵死了**。

---

## 二、根因 1：解锁条件 vs 测试台时序

`Src/main.c:1584-1585`（tenKhzRoutine）：

```c
if (adjusted_input == 0) {
    armed_timeout_count++;
    if (armed_timeout_count > LOOP_FREQUENCY_HZ) {   // one second（本 target = 20000）
        if (zero_input_count > 30) { armed = 1; ... }
```

`Src/main.c:1618` 的 `else { armed_timeout_count = 0; }` ⇒ **只要油门非 0，计时器每拍清零** ⇒
"连续约 1 秒零油门"是硬条件。`zero_input_count` 的自增在 `Src/signal.c:175-177`（DShot DMA 收完回调里），同样只在 `adjusted_input == 0` 时 ++。

而 F103 状态机（`test_esc/App/app_esc_test.c`）只在**自己复位后的前 3 秒**（IDLE）发 `DSHOT_VALUE_DISARM = 0`，
之后 `RAMP(48→target)` → `HOLD(target)` 一直发油门。
⇒ **每次重烧/复位电调时，F103 早就在发油门了，电调永远等不到零油门。**

### 修法（F103 侧）：把"零油门窗口"变成可控的

`g_dbg` 新增可写字段 **`hold_zero`（偏移 +120 ⇒ `0x200001FC + 120 = 0x20000274`）**：

- `hold_zero != 0` ⇒ 立刻回到 IDLE、每拍重置状态计时、只发 `DISARM(0)`（并保持）；
- 写 `0` 的那一刻 ⇒ 直接进 RAMP 开始爬坡（守卫期已经把解锁做完了）；
- 上电默认值 = `APP_ESC_TEST_HOLD_ZERO_DEFAULT`（**默认 1**，即"上电先守零油门，等放行"；
  想恢复以前"上电 3 秒自动爬坡"的行为，把这个宏改成 0）。
- 守零期间 `poll_inputs()` 照常跑 ⇒ 遥测照收、DShot 帧照发（电调不会因超时自复位）。

## 三、根因 2（★ 真正的死锁点）：零油门分支把 `old_routine` 钉成 1

`Src/main.c:1315-1316`（`comp_pwm == 0` 分支；`1345` 是对称的另一支）：

```c
if (input < 47 + (80 * eepromBuffer.use_sine_start)) {   // 零油门
    if (!eepromBuffer.comp_pwm) {
        duty_cycle_setpoint = 0;
        if (!running) {
            old_routine = 1;        // ★ 就是这里
```

起步（上游原文，改动前在 `Src/main.c:1250-1252`）：

```c
if (running == 0) {
    allOff();
    if (!old_routine) { startMotor(); }   // ★ 被上一句挡住就什么都不做
    running = 1;
```

**时序**：解锁恰好发生在"零油门满 1 秒"那一刻 ⇒ 之后是 `armed=1 && input=0 && !running`
⇒ 正中 `1316` ⇒ `old_routine = 1` ⇒ 油门一抬，`startMotor()` 被跳过
⇒ 不 `commutate()`、过零中断也不武装 ⇒ **现象就是 `armed=1`、`running=1`、`duty` 有值，但电机不换相、推不动**
（与交接里"duty 恒 2.7%、推不动转子"以及更早那次"硬写 RAM 骗到 running=1 但不动"完全吻合）。

**还有第二重伤害**：`PeriodElapsedCallback()`（`Src/main.c:956-957`）里

```c
if (!old_routine) { enableCompInterrupts(); }   // 闭环链的自我续接
```

⇒ `old_routine == 1` 时过零中断不再被重新武装，闭环只走一步就断。

> 上游语义：`old_routine == 1` = "用老的轮询换相自己起步"。那是给**有比较器**的板子留的；
> 本板没有比较器（三相里只有 C 相能进 COMP，见 `Inc/targets.h` 的 `USE_ADC_BEMF` 注释），
> 轮询起步不可靠 ⇒ 闭环必须走 `startMotor()` → 中断换相链。

### 修法（电调侧，只影响闭环版）

1. `startMotor()` 入口清 0：`Src/main.c:1011` 起，`old_routine = 0;` 落在 **`Src/main.c:1021`**，
   用 `#if !RM2027_OL_ARM_ONLY` 包住。
   放在 `startMotor()` 里而不是只改 `main()`：因为零油门分支（1316/1345）、失步分支（2400）、
   BEMF 超时分支（2617）**都会**把它钉回 1，只钉 `main()` 是治不住的（`main()` 里那句 `old_routine = 0`
   仍在，`Src/main.c:2221`）。
2. 起步处**无条件**调用 `startMotor()`：`Src/main.c:1273`（开环分支 `#if RM2027_OL_ARM_ONLY` 保持原样，
   换相由 `olStepTick()` 独占）。
3. 开环版（`RM2027_OL_ARM_ONLY=1`）行为**完全不变**。

## 四、附带修一处：斜坡目标 120 → 400

`duty = map(input, 47, 2047, minimum_duty_cycle, 2000)`，而闭环固件把 `minimum_duty_cycle` 钉成 0
（`Src/main.c:2207`）。

- 油门 120 ⇒ `map(120,47,2047,0,2000) = 73` ⇒ 占空比 **3.6%** —— 扭矩不够带起转子；
- 油门 400 ⇒ **353/2000 = 17.6%** —— 与开环台架验证过能转的 `OL_INPUT_RUN = 400` 一致，
  也正是交接里写的预期值 "`duty ≈ 353`"，且不超 `startup_max_duty_cycle = 400`（`Src/main.c:2213`）。

⇒ `test_esc/App/app_esc_test.h` 的 `APP_ESC_TEST_RAMP_TARGET` 改回 `400u`（README 里本来写的就是 400）。

## 五、上电测试步骤（照做）

前提：母线 **12 V、限流 1.5 A、不装桨**。

1. **先烧/复位 F103**（J-Link）。它上电默认 `hold_zero=1` ⇒ 一直发 `DISARM(0)`。
2. **复位/上电 ESC**（或刚烧完 app）。等 ≥1.5 s：读 `armed`(0x20000620) 应为 **1**（会响一声解锁音）。
3. 复核守零态：`newinput`=0、`input`=0、`adjusted_input`=0、`zero_input_count`>30、`cell_count`=0；
   此刻 `old_routine`(0x2000005C) = 1 是正常的（马上会被 `startMotor()` 清掉）。
4. **放行**：把 F103 的 **`0x20000274`**（= `g_dbg + 120`）写字节 `0`
   ⇒ F103 立刻从油门 48 爬升到 400（3 秒）。
5. 看 ESC：`running`(0x20000608) → 1、`duty_cycle`(0x20000610) ≈ **353**、
   **`zero_crosses`(0x20000604) 持续上涨**（这就是闭环跑起来的判据）、`old_routine` → 0、
   `e_rpm`(0x20000670) 上升；F103 侧 `telem_erpm_x100` 同步上升。
6. 异常处置顺序：
   - 不转 / 反转 ⇒ 写 `bemf_polarity_invert`(0x20000794)=1 再试（离线推导倾向它应为 1）；
   - 低速丢步 ⇒ `BEMF_HYST_LSB` 8→2~4（`Inc/targets.h`，需重编译）；
   - 仍不动 ⇒ 查起步瞬间 `average_interval`：它起步时为 0（`startMotor()` 里先 `commutate()`
     后赋 `commutation_interval`，所以 `commutation_intervals[]` 首值是 0），
     会让 `Mcu/g071/Src/stm32g0xx_it.c:244` 那个门槛
     `INTERVAL_TIMER->CNT > (average_interval >> 1)` 在最初几帧形同虚设 ⇒ 可能过早换相。
     （下一处要动的地方就是它。）

## 七、★ 上电复验（2026-10-07 当天，**两个根因都在硬件上坐实**）

当时母线**没上 12 V**（电调仅由 ST-Link 的 3.3 V 供电 ⇒ 只验解锁、不验转）。

### 7.1 根因 1 证实：给零油门窗口就解锁

用户复位（让 F103 重新给出前 3 秒零油门）后读到：

| 变量 | 值 | 判读 |
|---|---|---|
| `armed` | **1** | ★ **解锁成立** |

### 7.2 根因 2 证实：解锁后 `old_routine` 被钉成 1 ⇒ 起不来

同一次快照里（**旧电调固件**，即我改动前的版本）：

| 变量 | 值 | 判读 |
|---|---|---|
| `old_routine` | **1** | ★ 零油门分支 `main.c:1315-1316` 干的 |

| `bemf_irq_armed` | 0 | ★ 过零中断**没被武装** ⇒ 闭环链断在这 |
| `e_rpm` | ≈8 | 电机基本没转 |
| `bemf_timeout_happened` | **151** | 靠 BEMF 超时分支（`main.c:2613-2621`）每隔一阵硬踹一次换相 |

⇒ 与第三节的推断逐条对上：**解锁过程本身把 `startMotor()` 堵死了。**

> 附带澄清：当时 `battery_voltage = 277`（2.77 V）、`actual_current ≈ 0`
> ⇒ 12 V 母线是关着的（这 2.77 V 像是 ST-Link 的 3.3 V 串过来的）。
> 所以那次 `running = 1` 纯粹是逻辑状态，**电机本来也不可能转** —— 别把"不转"记在换相头上。

## 九、第一次带 12 V 的闭环试跑（2026-10-07）

### 9.1 修复生效了：`old_routine` 1→0

烧入带修复的新固件后放行油门，采样序列显示：

```
放行前  armed=1 run=0 duty=  0 zc=0 old=1 irq=0 newin=  0
放行1s  armed=1 run=1 duty= 87 zc=2 old=1 irq=0 newin=135 bemfTO=32
放行2s  ...            duty=177 zc=2 old=1 ...     newin=226 bemfTO=65
放行4s  ...            duty=351 zc=4 old=0 irq=1 newin=400 bemfTO=130   ← ★ old_routine 变 0
```

⇒ **`startMotor()` 被调用了、过零中断被武装了**，第三节那个"解锁即堵死"的死锁解开了。

### 9.2 但闭环没锁住：过零判不出来，靠超时分支硬踹

- `e_rpm` 恒 8（≈不转）；`bemf_timeout_happened` 以 **30~50 次/秒** 狂涨
- 母线电流明显升高：用户实测 **12 V 母线约 1 A**，电机"缓慢转但一直抖"
  （⚠ 电源限流设的是 **1.5 A** ⇒ **并没有顶到限流**，母线全程稳在 12 V
   ⇒ 不是"限流/塌压"造成的，纯粹是换相时序问题）
- `zero_crosses` 只在 1~4 之间反复（每次超时分支都把它清零）

> 顺带一个待查的小账：同一次试跑里，**电调自己的遥测电流只报 0.32~0.46 A**，
> 而电源显示约 1 A —— 差 2~3 倍。要么电源显示不准（低电流段），要么电调的
> 电流采样标定/零点（`CURRENT_OFFSET=0` 那个假设）需要重新对。不影响本轮定位，
> 但以后要精确限流保护时必须先把这个对上。

机理：闭环提速靠"真过零 → `interruptRoutine()` → COM_TIMER → `PeriodElapsedCallback()`
（每步把 `commutation_interval` 砍半）"。一次过零都认不出来 ⇒ 没有加速过程，
只剩 `INTERVAL_TIMER_COUNT > 45000` 那条"转不动"兜底分支每几十毫秒硬踹一次换相
⇒ 相位时序不同步 ⇒ 电机慢慢蹭着转 + 抖 + 电流大。

### 9.3 最可疑：滞回窗口 ≥ 信号幅度

读到的四路 BEMF 码（**注意：当时母线多数时间关着，所以这组数更接近"噪声底"**）：

```
va≈3~4   vb≈16~17   vc≈15~18   v0≈10~12   ⇒  delta = 悬空相 - V0 ≈ -6 ~ -9
bemf_hyst = 8   ← 滞回半宽
```

`adc_bemf.c:100-105` 的施密特是 `delta > +hyst` 才置 1、`delta < -hyst` 才置 0。
**delta 幅度(~7) < hyst(8)** ⇒ 永远翻不过去 ⇒ 认不出过零。
（`Inc/targets.h` 里自己写过"低速起步如丢步可降到 2~4"，正对应这里。）

⚠ 这组 delta 是在母线基本关着时读的，**必须先补一次"带电驱动时"的四路码测量**
（确认 delta 真的会摆动、摆多大），再定 hyst 的值 —— 别只凭这组数下结论。

`delta` 是否摆动、`zc` 是否持续上涨、`bemfTO` 是否不再涨、`e_rpm` 是否上升。

若四路码在带电驱动时**完全不动**，那问题在采样通路（`Inc/targets.h` 警告过：
占空比 < 约 27% 时 7 路扫描的尾巴会掉进关断期，而我们现在是 17.6%），
那就得先挪采样时刻（`ADC_TRIGGER_CCR4`）或加长导通期，再谈极性/滞回。

### 9.5 安全：每次都短促发 + 立刻锁回

堵转/时序不同步时母线电流会到 1 A 上下（限流 1.5 A ⇒ 未触顶），
按占空比 17.6% 折算相电流 ≈ 1/0.176 ≈ **5.7 A**，电机持续发热，所以：
- 每次放行有硬上限（脚本里 `DRIVE_MAX_S=6s`，实际只采 2~3 次 ≈ 2~3 s）
- 脚本用 `atexit` 保证任何异常退出路径都写回 `hold_zero=1`
- 手工锁回：写 F103 `0x20000274` = 1

## 十、★ 闭环首跑成功：一共五层死锁（2026-10-07）

| # | 层 | 现象 | 修法 | 验证 |
|---|---|---|---|---|
| 1 | 解锁窗口 | `armed=0`，永远不解锁 | F103 加 `hold_zero` 守零油门 | `armed=1` ✓ |
| 2 | 零油门分支钉 `old_routine` | `running=1` 但不换相 | `startMotor()` 入口清 0 + 起步无条件调用 | `old_routine` 1→0 ✓ |
| 3 | 超时分支把过零中断永久屏蔽 | `irq_armed` 恒 0、`zc` 卡 1~4 | 超时分支保持 `old_routine=0` 并重新武装 | `irq` 开始翻转 ✓ |
| 4 | **ADC 采样落在导通期之外** | `delta≈0`、悬空相/V0 读 0 | `COMMON_1` 19.5→7.5 周期、`ADC_TRIGGER_CCR4` 150→100、`BEMF_HYST_LSB` 8→4 | `V0 ≈ 三相均值`、`delta` 变 ±330 ✓ |

### 10.1 第 4 层的判据（值得记住）

四路 BEMF 是 rank1~4 **依次**采样，实测整条约 **3.6µs ≈ 230 拍**（COMMON_1＝19.5 周期时）。
必须满足 **`CCR4 + 230 < duty × 2665`**，否则尾巴（VC、V0）落进关断期，
导通期一结束星点就塌到 0 ⇒ `delta ≈ 0` ⇒ 判不出过零。**溢出时的特征现象**：
先采的 `vb` 能读到 ≈VBAT(1053)，后采的 `vc`、`v0` 恒为 0。
实测佐证：`CCR4` 提前到 60 后立刻自洽（`vb=717 vc=1051 v0=588`，均值 590 ≈ v0 ✓）。

### 10.2 第 5 层的机理

超时分支调 `zcfoundroutine()` 会写 `thiszctime = INTERVAL_TIMER_COUNT`（≈45000，即本次超时时刻）。
这个**假的过零时刻**随后被 `interruptRoutine()` 复制进 `lastzctime`，再被 `PeriodElapsedCallback`
的平滑式 `ci = (ci + ((lastzctime+thiszctime)>>1)) >> 1` 平均进 `commutation_interval`
⇒ ci 被不断**拉大** ⇒ 加速斜坡起不来。
实测配对证据：`lastzctime=45005 / thiszctime=18643`（45005 来自超时、18643 是真实过零）
⇒ 同时也证明了**过零本身是认到了的**（`interruptRoutine()` 确实在被调用）。

### 10.3 硬件配置核对（供以后参考，都在这块板上实测过）

- TIM1：`ARR=2665`、`COUNTERMODE_UP`、CH1-3 = PWM1/高有效 ⇒ 导通期从 CNT=0 起；
  `CCER=0x1555`（六路全开）、`BDTR` 死区 60 拍 ✓、`CCR4=150→100`（采样时刻发生器）
- ADC1：`CFGR1.EXTSEL=1`(TIM1_CC4)、`EXTEN=01`(上升沿)、`DMAEN=1`、`CHSELRMOD=1`；
  `CCR.PRESC=1`(÷2)、`TSEN=1`；RCC：SYSCLK=64MHz(PLL)、`ADCSEL=00(PLLP)` ⇒ ADC 时钟 32MHz
- `INTERVAL_TIMER = TIM2`：`PSC=31` ⇒ 2MHz 计数（即 0.5µs/拍，与代码里 ci 的单位一致）
- `COM_TIMER = TIM14`：`PSC=31` ⇒ 2MHz、`CEN=1`；`TIM14_IRQHandler → PeriodElapsedCallback()`
- `tenKhzRoutine()` 由 **TIM6** 中断驱动

### 10.4 还剩什么

### 13.1 新工具：live 模式（一个 openocd 会话里边跑边采）

（实测 openocd 的 TCL 支持 `sleep` ✓。）

### 13.2 机理：一次"迟到 190 倍"的假过零把 ci 一次性顶飞

40 次快照里 R34→R35→R36 是决定性的三行：

```
R34  ci=89     eRPM=2158   ← 转得好（步长约 45µs）
R35  ci=4447   avg=92      thiszc=17529
R36  ci=4128   eRPM=40     ← 掉进爬行，之后 1~3 秒才爬回来
```

R35 里 `ci=4447` 与 `avg=92` 自相矛盾（`avg` 由**已存**的换相间隔算出，仍是 92
⇒ 说明 `ci` 是在最后一次换相**之后**被单独改大的）。代入 `zcfoundroutine()` 的公式：

```
ci_new = (thiszctime + 3·ci_old)/4 = (17529 + 3×92)/4 = 4450   ← 实测 4447 ✓（对到个位数）
```

⇒ 一次"过零"是在上一步之后 **8.7ms** 才被认到的（正常步长 45µs ⇒ 190 倍），被当成有效值 ⇒
`ci` 一次顶到 4450 ⇒ 下一步 `waitTime = ci/2 ≈ 2200 拍` ⇒ 闭环瞬间瘫到爬行。
爬回来是因为过零又陆续被认到、`ci` 被缓慢拉回 ⇒ 于是形成 **1~3 秒一次的"掉速—爬回"循环**
⇒ 听感就是用户说的"在转、但一直抖、转速慢"。

### 13.3 修复：给过零判据加【上界】

`Mcu/g071/Src/stm32g0xx_it.c`：原来只卡下界（`CNT > avg/2`，防同一次过零重复计），
**没有上界** ⇒ 190 倍迟到的假过零畅通无阻。现改为窗口 `[avg/2, 2·avg]`：

```c
if (bemf_irq_armed
    && (INTERVAL_TIMER->CNT > (average_interval >> 1))
    && ((average_interval < 50) || (INTERVAL_TIMER->CNT < ((uint32_t)average_interval << 1)))
    && (getCompOutputLevel() == !rising)) { bemf_irq_armed = 0; interruptRoutine(); }
```

- 物理依据：真过零只会落在"上次换相之后半个到一个步长"附近（`average_interval ≈ 步长`）；
- 丢掉假过零时**保持武装**（本周期/下周期再判），没有就交给 22.5ms 超时兜底；
- `average_interval < 50 拍`（起步/异常）时上界无意义，不卡。

**但实测数据自相矛盾**（`live` R24 那行，step=2：A 应悬空、B 应低、C 应高）：

```
va =   9 码 (≈0 V)    ← A 应悬空、应 ≈ VBAT/2 ≈ 474 码，却是 0 ⇒ 被低边钳住、根本没悬空
vb = 118 码 (≈1.5 V)  ← B 是低边相，应 ≈ 0
vc = 945 码 (≈VBAT)   ✓ C 是对的
```

⇒ **"悬空相被钳住"才是真因**：它盯着的"过零"全是驱动的开关沿 ⇒ 换相时刻全错 ⇒ 原地抖。
与"开环能正常转（时间驱动、完全不依赖 BEMF）"完全自洽。

### 15.3 下一步：用【静态】驱动状态定性（不再靠动态数据猜）

动态跑的时候换相一直在走，很难判。要**把一个六步状态钉住**（不让它换相），
然后读三路相电压 —— 正确的话应该是 (VBAT, 0, ≈VBAT/2) 三个清晰电平：

1. 用调试器直接把 TIM1/GPIO 拨到某个状态（例如 step2：A 两脚输出低、B 低边输出高、
   C 高边走 TIM1_CH1），再读 va/vb/vc —— 这一步能干净地区分
   "① 悬空相当的没悬空" 还是 "② 相的顺序被置换了"。
2. 更直接：**用示波器看 MOTORA/B/C 三点的相电压**（台架有示波器），
   正常六步应该是三相互相错开 120° 的阶梯波，每相各有 1/3 时间悬空（≈VBAT/2）。

### 15.4 门极映射也用网表核对了（全对）

| 固件"相" | 高边脚 | 低边脚 | 驱动器输入 | 电机相 |
|---|---|---|---|---|
| A | PA10 (TIM1_CH3) | PB1 (CH3N) | HIN1(U2-22)/LIN1(U2-1) | **MOTORA** ✓ |
| B | PA9 (CH2) | PB0 (CH2N) | HIN2(U2-23)/LIN2(U2-2) | **MOTORB** ✓ |
| C | PA8 (CH1) | PA7 (CH1N) | HIN3(U2-24)/LIN3(U2-3) | **MOTORC** ✓ |

 上面这张表是按网表原始行逐条读出来的。）

加上 15.2 的三条 ⇒ **代码与硬件的映射层面全部一致**：
- 门极脚↔驱动器↔电机相 ✓
- 采样脚↔电机相（MOTORA→PA5、B→PA4、C→PA2、星点→PA3）✓
- 六步表 `comStep()` ↔ `changeCompInput()` ✓
- `phaseAFLOAT()`（`PWM_ENABLE_BRIDGE` 未定义那一支）✓

### 15.5 ⇒ 所以"动态快照"这条路已经到头了，必须换静态法

映射全对，但动态快照里"固件说悬空的相"读到 ≈0V。除了"悬空相真被钳住"之外，
还有一个**同样成立的解释**：**快照比较的是两个不同时刻的状态**——
ADC 是在每个 PWM 周期的 CNT=CCR4 处采样（采到的是**当时那一相/那个 step** 的电压），
而我读 `step`/`active_phase` 是在 halt 之后（**可能已经换到下一步**）
⇒ "用新 step 的 ap 去解释旧 step 的采样值" ⇒ 自然会得出"该相没悬空"的错误结论。

两种解释靠动态数据**无法区分** ⇒ 下一步必须用【静态】状态定性：

**方案 A（我来做）**：用调试器直接拨 TIM1/GPIO 到某个固定的六步状态（不让它换相），
再读 va/vb/vc。正确的话应是三个清晰电平：**一相 ≈VBAT(≈950 码)、一相 ≈0、一相 ≈VBAT/2(≈474 码)**。
- 若悬空相读到 ≈474 ⇒ 硬件/映射都对，问题在别处（换相时序/极性）；
- 若悬空相读到 ≈0 ⇒ "悬空相没悬空"坐实，回到 `phaseAFLOAT()` 的实际效果上查。

**方案 B（你做，更快）**：示波器直接看 **MOTORA/MOTORB/MOTORC 三相电压**。
正常六步是三个互相错开 120° 的阶梯波，**每相各有 1/3 时间悬空在 ≈VBAT/2**。
一眼就能看出：是不是有一相从来不悬空、或者相的次序不对。
