# 07 · 「传感器总线没注册」是误判 —— 真因与修复

> 日期：2026-09-29 晚（会话 4）
> 触发：用户新证据 —— `ls /dev` 里**没有** `spi1` / `i2c-2` / `i2c-4`，
> 三个驱动都报 `Not running` / `no instance started`。
> 用户的假设：**传感器总线压根没注册**（并据此认为上一轮"器件坏"的结论被推翻）。
> **本文结论（一句话）**：`/dev/spi1`、`/dev/i2c2`、`/dev/i2c4` **在 PX4/NuttX 上永远不会出现**，
> 这跟"总线有没有注册"无关 —— 它是 NuttX 的**测试用字符设备**，PX4 **一条板子都没开**。
> ⇒ 新证据**不成立**，上一轮关于 ICM 的结论**没有被推翻**。
> 但本轮确实挖出一个**真 bug**（而且是"总线选不上"这一类，只是和 `/dev` 无关）：
> `rc.board_sensors` 里 **`ist8310 -X -b 4`** 用错了标志 —— `-X`（external）在
> 一条 external I2C 总线都没有的板子上**一次总线都匹配不到**，磁罗盘**根本没被 probe 过**。
> 已改为 `-I`（internal），**重建 + 重烧已上板**，并用控制台环形缓冲验证新固件已生效。

## 一、先回答核心问题：这些设备节点是谁创建的？

用户问的是二选一：**(a) 开板时 board 层主动注册；还是 (b) 驱动首次调用
`stm32_spibus_initialize()` / `stm32_i2cbus_initialize()` 时惰性创建？**

**答案：两个都不是。** 这是第三种可能：

```text
/dev/spiN  由 spi_register() 创建   → drivers/spi/spi_driver.c:352
/dev/i2cN  由 i2c_register() 创建   → drivers/i2c/i2c_driver.c:394
（注意名字：NuttX 是 /dev/spi%d 和 /dev/i2c%d，**没有横杠** —— 用户写的 i2c-2/i2c-4
  是 **Linux 的** i2c-dev 命名习惯，NuttX 不是这个格式）
```

这两个 register 函数**只有两个前置条件**，缺一不可：

1. **Kconfig 开关**（编译期）：
   ```text
   drivers/spi/Make.defs:29-30   ifeq ($(CONFIG_SPI_DRIVER),y)  → CSRCS += spi_driver.c
   drivers/i2c/Make.defs:29      ifeq ($(CONFIG_I2C_DRIVER),y)  → CSRCS += i2c_driver.c
   ```
   而这两个开关在 Kconfig 里的帮助文字写得非常直白（`drivers/spi/Kconfig:227-235`）：
   ```text
   config SPI_DRIVER
       bool "SPI character driver"
       default n                       ← ★ 默认关
       ---help---
         Build in support for a character driver at /dev/spi[N] ...
         The intent of this driver is to support SPI testing.
         It is not suitable for use in any real driver application.   ← ★ 官方明说"不适合真驱动用"
   ```
   `CONFIG_I2C_DRIVER` 的帮助文字同款（`drivers/i2c/Kconfig:117-124`），也是 `default n`。

2. **有人显式调用 register 函数**。而：
   - `stm32_i2cbus_initialize()`（`arch/arm/src/stm32h7/stm32_i2c.c:2718`）**只** kmm_malloc 一个
     instance、`stm32_i2c_init()` 上电配 GPIO 并 refs++，**全文没有 i2c_register**。
   - `stm32_spibus_initialize()`（`arch/arm/src/stm32h7/stm32_spi.c:2599`）同理，
     **整个 `arch/arm/src/stm32h7/` 目录里 `spi_register` 出现 0 次**。
   - PX4 自己也从来不调：`grep -rn "spi_register\|i2c_register" platforms/ src/ boards/`
     在 PX4 代码里命中 0 处（只命中 NuttX 树里别的架构的 board bring-up）。

**⇒ 所以：**

| 问题 | 答案 |
|---|---|
| `/dev/spi1` 是开板时注册的吗？ | 不是 |
| `stm32_spibus_initialize()` 会顺手建 `/dev/spi1` 吗？ | **不会** |
| PX4 有没有哪块板上出现过 `/dev/spi1`？ | **没有**。`grep -rln "CONFIG_SPI_DRIVER=y\|CONFIG_I2C_DRIVER=y" boards/` **零命中** |

**"没有 `/dev/spi1`" 是 PX4 的常态，不是故障现象** ⇒ 它既不证明总线没注册，
也不能当证据用。用户的推理链在第一步就断了。

## 二、证据链（4 条独立证据）

### 证据 1 · 我们自己的构建配置（编译期）

```text
build/rm2027_fmu-h743_default/NuttX/nuttx/.config
  L878  # CONFIG_I2C_DRIVER is not set
  L897  # CONFIG_SPI_DRIVER is not set
```

### 证据 2 · 我们自己的 ELF 符号表（链接期，最硬）

```text
$ arm-none-eabi-nm -C build/rm2027_fmu-h743_default/rm2027_fmu-h743_default.elf | grep -E "spi_register|i2c_register|spibus_initialize|i2cbus_initialize"
0812648c T stm32_i2cbus_initialize      ← 总线初始化在
08129dc4 T stm32_spibus_initialize      ← 总线初始化在
（spi_register / i2c_register 一个字都没有）
```

**总线初始化函数被链接进去了，注册函数压根没编进来** —— 这份固件**物理上不可能**
建出 `/dev/spi1`。这条证据不依赖任何推理。

### 证据 3 · 运行时寄存器：SPI1 确实被初始化了

ST-Link 只读（`halt` → `mdw` → `resume`，**本轮没有写任何寄存器**）：

| 寄存器 | 地址 | 值 | 解读 |
|---|---|---|---|
| `RCC_APB2ENR` | 0x580244F0 | `0x00001031` | **SPI1EN(bit12)=1** ⇒ SPI1 时钟已开 |
| `SPI1_CR1` | 0x40013000 | `0x00001201` | **SPE(bit0)=1** ⇒ SPI1 外设已使能 |
| `GPIOB_MODER` | 0x58020400 | `0xFA0FFDBF` | PB3=AF、PB4=输出 |
| `GPIOB_AFRL` | 0x58020420 | `0x00005000` | PB3=AF5=SPI1_SCK |
| `GPIOB_ODR` | 0x58020414 | `0x00000C10` | PB4(CS)=1 空闲高 |
| `GPIOA_AFRL` | 0x58020020 | `0x05000000` | PA6=AF5=SPI1_MISO |
| `GPIOD_AFRL` | 0x58020C20 | `0x50000899` | PD7=AF5=SPI1_MOSI |

**只有 `stm32_spibus_initialize()` 跑过，这些位才可能是这个样子**（AF5 + SPE）。
⇒ **SPI1 总线（NuttX 意义上的 `spi_dev_s`）是注册好的**。它只是不叫 `/dev/spi1`。

### 证据 4 · 控制台环形缓冲（★ 本轮新手段，拿到了真实开机日志）

PX4 的 `BOARD_ENABLE_CONSOLE_BUFFER` 会把 stdout 存进 RAM 环形缓冲（`dmesg` 读的就是它）。
符号 `g_console_buffer @ 0x2400A2C4`（`.bss`），类布局：
`char _buffer[4096]` + `int _head` + `int _tail`。

`dump_image 0x2400A2C4 4224` 后按 `head/tail` 还原，得到 **本次开机** 的完整日志：

```text
HW arch: RM2027_FMU_H743
...
Board sensors: /etc/init.d/rc.board_sensors
ERROR [SPI_I2C] icm42688p: no instance started (no device on bus?)
ERROR [SPI_I2C] ist8310: no instance started (no device on bus?)      ← ★ ERROR，不是 WARN
ERROR [SPI_I2C] spa06: no instance started (no device on bus?)
...
ERROR [init] No airframe file found for SYS_AUTOSTART value
ERROR [ekf2] start failed (-1)
```

两条关键信息：

1. **`head = 0`**（缓冲从没绕过圈）⇒ 这是**几分钟前刚开机**的日志，不是几十分钟前的残留。
2. **`ist8310` 那行是 `ERROR`**，而用户手工敲 `-X` 时是 `WARN` —— 这个差别是**有源码依据的**
   （见第四节）：`-X` 只可能打 WARN，`-I` 只可能打 ERROR。
   ⇒ **板子已经在跑"改成 `-I` 之后"的新固件**，修复已上板。

## 三、被误读的那两个"没出现"的 I2C 节点

用户还看到 **I2C2/I2C4 的时钟使能位是 0**，据此认为"根本没人调用初始化"。
这个推理**也是错的**，源码在这里：

```text
platforms/nuttx/src/px4/common/px4_init.cpp:87-113   px4_platform_i2c_init()
  while (i2c_bus_iterator.next()) {
      i2c_master_s *i2c_dev = px4_i2cbus_initialize(i2c_bus_iterator.bus().bus);  ← 上电
      I2C_RESET(i2c_dev);
      I2C_TRANSFER(... 软复位 ...);
      px4_i2cbus_uninitialize(i2c_dev);                                          ← ★ 立刻关掉
  }
px4_init.cpp:160   px4_platform_init() 里调用它（CONFIG_I2C && !BOARD_I2C_LATEINIT）
```

而 `stm32_i2cbus_uninitialize()` → `stm32_i2c_deinit()`（`stm32_i2c.c:2202`）干了三件事：

```c
stm32_i2c_putreg32(priv, STM32_I2C_CR1_OFFSET, 0);   // CR1=0，外设关闭
stm32_unconfiggpio(priv->config->scl_pin);           // SCL 回默认态
stm32_unconfiggpio(priv->config->sda_pin);           // SDA 回默认态
modifyreg32(priv->config->clk_reg, priv->config->clk_bit, 0);   // ★ 关时钟
```

**⇒ 开机之后 I2C2EN=0 / I2C4EN=0 / PB10,PB11,PD12,PD13 回到复位默认（input, AF0）
是"初始化过又主动释放"的正常终态**，不是"没人初始化"。

我实测到的正是这个状态（与推理完全吻合）：

```text
RCC_APB1LENR (0x580244E8) = 0x00140001   → I2C2EN(bit22)=0
RCC_APB4ENR  (0x580244F4) = 0x00010002   → I2C4EN(bit7)=0
GPIOB_MODER  PB10/PB11 = 00（input）、GPIOB_AFRH 里这两位 AF=0
GPIOD_MODER  PD12/PD13 = 00（input）、GPIOD_AFRH 里这两位 AF=0
I2C2_CR1 (0x40005800) = 0；I2C4_CR1 (0x58001C00) = 0
```

**另有一条独立证据证明 `px4_platform_i2c_init()` 确实跑过**：
用户的 `ls /dev` 里**有 `console_buf`**。它由 `px4_console_buffer_init()`（`px4_init.cpp:127`）
注册；而 `px4_platform_i2c_init()` 在**同一函数、更靠后**的第 160 行。
`console_buf` 在 ⇒ 这个函数跑到底了 ⇒ **`stm32_i2cbus_initialize(2)` 和 `(4)` 开机时都被调用过**。

## 四、★ 本轮真正的发现：`ist8310 -X` 是错的（总线选不上）

### 4.1 现场症状的不对称

用户给的三条报错，**日志级别不一样**：

```text
icm42688p -s -b 1 ... → ERROR     ← internal
ist8310   -X -b 4 ... → WARN      ← ★ external
spa06     -I -b 2 ... → ERROR     ← internal
```

这个差别不是随机的，源码写死了（`platforms/common/i2c_spi_buses.cpp:764-772`）：

```cpp
if (!started && !cli.quiet_start) {
    static constexpr char no_instance_started[] {"no instance started (no device on bus?)"};
    if (iterator.external()) { PX4_WARN(...); }   // ← -X / -S 走这里
    else                     { PX4_ERR(...);  }   // ← -I / -s 走这里
}
```

### 4.2 为什么 `-X` 在**这块板**上必然一个总线都匹配不到

```text
boards/rm2027/fmu-h743/src/i2c.cpp:
    initI2CBusInternal(2)   →  bus=2, topology=Internal（SPA06 气压计）
    initI2CBusInternal(4)   →  bus=4, topology=Internal（IST8310 磁罗盘）
    ★ 全板**一条 External / Shared I2C 总线都没有**
```

`platforms/common/i2c.cpp:53-99` `I2CBusIterator::next()` 的 ExternalBus 分支：

```cpp
case FilterType::ExternalBus:
    if (bus_topology_has_external(topology)) {   // ← 唯一的进门条件
        ++_external_bus_counter;
        if (bus_matches) { return true; }
    }
    break;
```

而 `platforms/common/include/px4_platform_common/bus_topology.h:69-72`：

```cpp
static inline constexpr bool bus_topology_has_external(BusTopology topology)
{
	return topology != BusTopology::Internal;     // Internal ⇒ false
}
```

⇒ `-X` 时循环体**一次都不执行**，`iterator.next()` 立刻返回 false，
`started` 保持 false，然后按 `external()==true` 打 **WARN**。

**这解释了现场每一个字**：ist8310 报 WARN + "no instance started"，
**但它从来没碰过 I2C4，也从来没 probe 过那颗 IST8310**。
这条报错**不能用来判断磁罗盘好坏、也不能用来判断 I2C4 总线好坏**。

### 4.3 参考板怎么写（板载磁罗盘一律 `-I`）

```bash
$ grep -rn "ist8310" boards/*/*/init/rc.board_sensors
boards/px4/fmu-v5/init/rc.board_sensors:28:          ist8310 -I -R 10 start        ← 板载
boards/corvon/743v2/init/rc.board_sensors:25:        ist8310 -I -b 2 -a 0x0E -R 2 start   ← 板载，显式 -b
boards/atl/mantis-edu/init/rc.board_sensors:12:      ist8310 start -I -b 2 -R 14   ← 板载
boards/holybro/durandal-v1/init/rc.board_sensors:27: ist8310 -I -R 10 start        ← 板载
boards/auterion/fmu-v6s/init/rc.board_sensors:77:    ist8310 -X -b 1 -R 10 start   ← 这些 -X 都是**外置**磁罗盘（接在 external 总线上）
```

`-X` 的正确用法是"探外接罗盘"；我们把它用在板载器件上，**方向反了**。

## 六、上一轮结论：哪条错了、哪条没错（诚实交代）

### 6.1 错的（本轮的误判 + 上一轮的一处错）

| # | 说法 | 对错 | 依据 |
|---|---|---|---|
| E-1 | 「`/dev` 里没有 spi1/i2c-N ⇒ 总线没注册」（本轮） | **❌ 错** | `CONFIG_SPI_DRIVER/I2C_DRIVER` 都没开；ELF 里连 `spi_register` 符号都没有；PX4 全家族板子都没有这些节点 |
| E-2 | 「I2C 时钟是 0 ⇒ 没人调用初始化」（本轮） | **❌ 错** | `stm32_i2c_deinit()` 主动关时钟；`/dev/console_buf` 存在证明 `px4_platform_i2c_init()` 跑过 |
| E-3 | 「用 `icm42688p ... -d start` 能打印 WHO_AM_I」（06 号日志 Q4） | **❌ 错，别照做** | `BusCLIArguments::getOpt` 组出来的选项串里**没有 `d`**；`icm42688p_main.cpp:58` 只传 `"C:R:6"`；全仓库**没有任何地方把 `Device::_debug_enabled` 置 true**（`Device.hpp:284` 默认 false）⇒ `DEVICE_DEBUG("unexpected WHO_AM_I ...")` 永远不会打印 |

> E-3 是上一轮留下的**错误操作建议**：`-d` 不是合法选项，敲了只会让模块打印用法后退出。
> 想拿到 WHO_AM_I 只能靠调试器（06 号日志第二节那套事务）。

### 6.2 没错的（没被新证据推翻）

- **上一轮关于 ICM-42688-P 的结论（"器件能应答 SPI，但不实现 ICM-42688-P 的寄存器接口"）
  没有被新证据推翻**：新证据（`/dev` 无节点）已经被证明与总线注册无关（E-1），
  它**不构成**对上一轮任何一条寄存器读数的反驳。
- 但要说清楚：**本轮我没有重新做那套调试器级 SPI 事务**（用户本轮限定"只读，不要改任何寄存器"），
  所以上一轮那条最硬的证据（写 0x75/0x76 回读）本轮**既没被复核、也没被推翻** —— 仍是"存疑但成立"。
- 同理，`spa06 -I -b 2` 的失败**不是** `-X` 那种标志错误（`-I` 用对了），
  它要么是器件不应答，要么是 I2C2 有硬件问题 —— 需要 `i2cdetect -b 2` 来分。

### 6.3 怎么发现的（发现路径）

```text
用户给的新证据 → 我先不信任何结论，只查"这些节点到底谁创建"

  → 回头逐条对比三条报错的日志级别（ERROR/WARN 不对称）→ 定位到 -X
  → 顺带发现上一轮遗留的 -d 建议是错的
```

## 七、负结果（试过/查过/排除，别再花时间）

| # | 怀疑 | 结论 | 依据 |
|---|---|---|---|
| M-01 | `/dev/spi1` 缺失 = SPI1 总线没注册 | **❌ 排除** | 证据链第二节；SPI1EN=1、SPE=1、PB3/PA6/PD7=AF5 |

## 十、本轮顺带发现（**独立问题**，没修，仅登记）

开机日志（证据 4）里还有几条与传感器无关、但**会挡住下一步**的问题：

| # | 日志 | 含义 | 影响 |
|---|---|---|---|
| S-1 | `INFO [param] parameter storage empty, initializing` + `ERROR [param] open backup '' failed (6)` + `ERROR [init] param load-or-init failed` | 本板**没有参数持久化**：`CONFIG_MTD is not set`（build `.config` L999）、`default.px4board` 里没有 `CONFIG_BOARD_PARAM_FILE`（本板无 SD）、`board_config.h` 的 `FLASH_BASED_PARAMS` 是**注释掉的** | 参数**掉电即失**。`SYS_AUTOSTART` 存不住 |
| S-2 | `ERROR [init] No airframe file found for SYS_AUTOSTART value` + `No autostart ID found` | SYS_AUTOSTART=0（S-1 的后果；airframes 本身**是**打包好的，`build/.../etc/init.d/airframes/` 有 38 个含 `4001_quad_x`） | 不设 airframe ⇒ **EKF2 起不来**（日志里 `ERROR [ekf2] start failed (-1)`）⇒ 连传感器正常也上不了天 |
| S-3 | `ERROR [dataman] dataman start failed` / `WARN Missing FMU SD Card` | 本板无 SD 卡 | 已知，不影响本轮 |

> S-1 的"正解"需要给参数划一个 flash 分区（MTD + `FLASH_BASED_PARAMS`），
> 这会**动到 linker 的 FLASH 长度**（现在是 1920K，正好顶到 flash 末尾）——
> 属于"不动链接地址/bootloader 布局"的边界之外，**本轮没做**，留给 Lead 决策。
