# `src/drivers/imu/bosch/bmi270/` —— ★ **死代码**：整条被推翻的路线（教学用）

> **运行时一句话**：**它什么都不做，因为它根本没被编进固件。**
> 这里存在的唯一理由是：**它是本项目最贵的一次弯路，值得留档**。
> 行号基准 `源码根（见 `tools/source-root.conf`）` HEAD `3b5de24`。

## 3. 它错在哪（技术层面，逐条都有出处）

### 3.1 起点就错了：把"WHO_AM_I 读不出来"当成"是 BMI270 兼容件"

| 步 | 当时的推理 | 实际 | 出处 |
|---|---|---|---|
| 1 | 原理图标 `ICM-42688-P`，但读 `0x75`（`WHO_AM_I`）得到 `0x00`，复位后还是 `0x00` | —— | [`boards/rm2027/fmu-h743/src/spi.cpp:49`](bmi270.md#^src-boards-rm2027-fmu-h743-src-spi-cpp-49) |
| 2 | 于是猜"这是 BMI270 的寄存器图兼容件"（`CHIP_ID(0x00) = 0x00` 而非正品 `0x24`） | **`0x00` 根本不是寄存器** —— 手册 §4.1 的通用寄存器表从 `0x01` 开始 | `rc.board_sensors:35-37`；手册 `HXY:713` |
| 3 | 给 `probe()` 加"兼容件"分支：`0x01 == 0x6A` **或** `0x00 == 0x00` 都认 | 兜底条件 `0x00 == 0x00` **恒真** ⇒ 什么都认 | [`BMI270.cpp:279`](bmi270.md#^src-src-drivers-imu-bosch-bmi270-BMI270-cpp-279)（`:292` 判 `CHIP_ID != chip_id`，`:297-306` 放行） |
| 4 | 真相：器件 ID 在 **`WHO_AM_I(0x01) = 0x6A`**，是**华轩阳自有寄存器图**，不是 BMI270 | 整个前提作废 | `HXY:846-850`（§5.1） |

**⇒ 这跟 `ist8310` 那次"`af9838` 的 probe 不校验 ID"是**同一个错误类型**：
`probe()` 放行了不该放行的东西。区别是这里放行的是**恒真条件**，比"不比较"更隐蔽。

### 3.2 ★ 最致命的一行：重复样本当成成功

```c
// BMI270.cpp:1063-1071（存档版）
if ((buffer.data[0] == _last_data[0]) && ... && (buffer.data[11] == _last_data[11])) {
    perf_count(_duplicate_sample_perf);
    return true;   // 不是错误：只是这一拍器件还没更新       ← ★ 这里
}
```

**后果链**（本项目纪律第 11/12 条）：
```
器件停转 → 寄存器保持旧值 → 每拍都判"重复" → return true（= 当成成功）
        → error_count 不增长、Reset() 永不触发
        → "器件死了"被伪装成"器件很安静"
        → duplicate sample 累计 400 万次，而 sensors 侧看到的是一切正常
```

**⇒ 新驱动（`hxy42688p`）明确否定这个写法**：
[`HXY42688P.cpp:556`](bmi270.md#^src-src-drivers-imu-hxy-hxy42688p-HXY42688P-cpp-556) 加了一整段注释：
> *"⚠️ 关键：这里【不再】像旧 bmi270 兼容补丁那样'重复就返回成功'，否则'器件死了'会被伪装成'器件很安静'。返回 false 会让活体保护开始计时。"*

### 3.3 其他被推翻的具体决定（存档 commit 里留着"已撤回"标记）

| 项 | 当时 | 结局 | 出处 |
|---|---|---|---|
| `ACCEL_COMPAT_GAIN_CORRECTION = 2048/1185 ≈ 1.7283`（单点增益修正） | 想修标度 | **已撤回 / 已删除** | [`BMI270.hpp:99`](bmi270.md#^src-src-drivers-imu-bosch-bmi270-BMI270-hpp-99)（"⛔【已撤回】…已删除"） |
| 量程 `±16g → ±4g` 且"只 set 不清" | 改不动 | 后来修了 | commit `c96dc03` |
| 写 `PWR_CONF(0x7C)` | BMI270 正品有 | **本片根本没有 0x7C** ⇒ 白写 | [`BMI270.hpp:119`](bmi270.md#^src-src-drivers-imu-bosch-bmi270-BMI270-hpp-119)；commit `f505644` |
| `set_range()` 被误乘增益系数 | —— | 后来修正 | commit `d909daf` |
| 温度字节序 / `PWR_CTRL` 启动时序 | upstream 缺陷 | 后来"按手册补" | commit `e567d41` |
| "这颗没有 FIFO" | 写进注释 | **是错的**，FIFO 在 `0x1C~0x21` | commit `57686a6`；`rc.board_sensors:40` |

**⇒ 看这些 commit 顺序能看出一种典型的救火模式**：
每发现一个不符，就加一条特判；特判越加越多，而**根因（"这不是 BMI270"）一直没被质疑**。
直到拿手册回原文，才发现整条路线的前提是错的。

## 4. 这条死路留下什么（可复用的正面遗产）

| 遗产 | 去哪了 |
|---|---|
| `probe()` 必须校验 ID | 变成纪律第 1 条；`ist8310` 用上了 |

**⇒ 一句话总结**：**12 个 commit、2044 行、存活率 100%，净产出是 0 个功能和 6 条纪律。**
