# H104 完整帧抓取方案（不丢字节）

> 目录：`work/spi-runtime/`　｜　建立：2026-09-30
> 目的：拿到一份**结构上不丢字节**的 USART1(=PA10) 字节流，用来验证 `H104-帧格式规格.md` 的 HI91 帧格式。
> 前置结论：`H104-帧格式规格.md` §7 —— 旧的 SWD 轮询抓包（453 字节）**不可用于组帧**。

---

## 0. 为什么不能再在 SWD 里轮询（量化）

| 量 | 值 |
|---|---|
| 115200 8N1 每字节时间 | 10 bit / 115200 = **86.8 µs** |
| HI91@100 Hz 数据率 | 82 × 100 = **8200 B/s**（71% 的串口带宽） |
| 一次 SWD 单寄存器读的耗时 | 约 **0.5 ~ 1 ms**（700 次循环抓 453 字节，脚本自己也统计到 `ORE=297/900`） |
| ⇒ 每次轮询期间到达的字节数 | **约 6 ~ 12 个** |
| ⇒ 每次实际拿到 | **1 个**（FIFO/单字节寄存器里最老那个），其余被 ORE 丢掉 |

**⇒ SWD 轮询的采样率天生比数据率低一个数量级，任何"多抓几次"都补不回来。**
必须让**板上的 NuttX 串口驱动**（中断驱动 + RX 环形缓冲，`CONFIG_USART1_RXBUFSIZE=600`）或 DMA 来收，
SWD 只负责"事后把 RAM 里的缓冲区搬走"。

## 1. 三个方案

| 方案 | 需要什么 | 工作量 | 推荐度 |
|---|---|---|---|
| **A1：`h104cap` 抓进固定 RAM 缓冲 + SWD dump** | ST-Link + build | 已写好草稿（见 §3） | ★★★ **推荐** |
| **A0：现成 `serial_test` 打 hex 到 console** | ST-Link + build（要开一个 config） | 只改 1 行配置 | ★★ 快速第一眼 |
| **B：USB-TTL 直接接 H104 的 TX，主机侧抓** | **需要用户动手接线** | 用户 5 分钟 | ★ 备选 |

**A0 与 A1 的差别**：A0 的字节要经过 console 环形缓冲，量大时会被覆盖（只能看到尾巴）；
A1 把原始字节钉在固定 RAM 地址上，**一个字节都不会因为 console 带宽丢掉**。

## 2. 纪律检查（**每一步之前都要做，出过两次事故**）

```bash
pgrep -a openocd        # 必须为空 —— 两个 openocd 抢同一个 ST-Link 会把它从 USB 上搞掉，要物理拔插
pgrep -a -f make        # 必须为空 —— build 目录只有一个，并发编译会损坏它
```

- ❌ **不碰 `/dev/ttyUSB0`**（用户的 QGC 独占）
- ❌ **不碰 SPI1 / BMI270 那条线**（另一个成员的地盘）；`CR1` 应为 `0x1001`，任何"读出来全 0/全 FF"先查主机侧 SPI1
- ❌ **不改 USART1 的引脚定义**（`board_config.h` / `nuttx-config/include/board.h`），**不改链接脚本**
- ✅ 只用：`USART1`（`PA10` RX / `PB6` TX）+ 一个小 RAM 缓冲 + ST-Link 读内存
- ⚠️ ST-Link **同一时间只允许一个成员持有**；用之前**先跟 Lead 报备**

## 3. 方案 A1：`h104cap`（推荐）

### 3.1 落码位置

草稿在 `h104/code-draft/h104cap/`（本期**没有**直接放进 PX4 树，因为另一个成员正在同一棵树上编译 IMU 实验，
**不在别人工作时改他的工作树**）。硬件/编译空出来之后照下面放：

```bash
PX4=~/桌面/RM2027/PX4-Autopilot
cp -r work/spi-runtime/h104/code-draft/h104cap  "$PX4/src/systemcmds/h104cap"
# 在 boards/rm2027/fmu-h743/default.px4board 的 SYSTEMCMDS 段插入（该文件按字母序）：
#   CONFIG_SYSTEMCMDS_H104CAP=y
```

PX4 的 Kconfig 是**自动 glob**（`src/systemcmds/Kconfig` 里就是 `rsource "*/Kconfig"`），
所以新建目录后不需要改任何中央清单；`cmake/kconfig.cmake` 会把
`CONFIG_MODULES_SYSTEMCMDS_H104CAP` 还原成路径 `systemcmds/h104cap`。
（板级配置文件里 CONFIG 名省掉 `MODULES_` 前缀，写 `CONFIG_SYSTEMCMDS_H104CAP=y` 即可。）

### 3.2 开机自动抓（不依赖 GCS / shell）

本板 console 不在 USART1 上（USART1 完全让给 H104），所以**不要指望在串口里手敲命令**。
用板级启动脚本自动跑 —— 加到 `boards/rm2027/fmu-h743/init/rc.board_extras` 末尾：

```sh
# H104 协议抓包（临时诊断；验完删掉）
h104cap capture -b 115200 -s 3
```

之后**重启板子**，它会在启动约 3 秒后把 8 KB 原始字节抓进 `g_h104_cap_buf` 并打印统计。
统计文本用现成的 `checklog.sh`（走 ST-Link 读 console 环形缓冲）就能看到。

### 3.3 把原始字节搬出来（SWD，不依赖 GCS）

```bash
PX4=~/桌面/RM2027/PX4-Autopilot
ELF="$PX4/build/rm2027_fmu-h743_default/rm2027_fmu-h743_default.elf"

# 1) 拿符号地址
nm "$ELF" | grep -E "g_h104_cap_buf|g_h104_cap_len|g_h104_cap_overflow"
#   例：  2400a100 b g_h104_cap_buf
#         2400c100 b g_h104_cap_len

# 2) dump（openocd 里；**先 pgrep 查 openocd 为空**）
#    dump_image h104-cap.bin 0x2400a100 0x2000
```

⚠️ 注意：缓冲区是**静态 .bss**，开机后被 PX4 的其他 BSS 清零流程覆盖过也没关系（我们在 rc.board_extras 里才写它）。
dump 时如果板上还在抓（`-s 3` 应该早结束了），拿到的是"抓完即静止"的快照 —— 这是有意的。

### 3.4 顺手把模块的真实配置问出来（★ 这一步最便宜、信息量最大）

用同一个工具发 ASCII 命令（**TX = PB6，板上已连到 H104**）：

```sh
h104cap cmd "LOG VERSION"      # PNAME / BUILD / UUID / SN / APP_VER / BL_VER
h104cap cmd "LOG COMCONFIG"    # 当前 BAUD、各帧 ONTIME(ms)、HI83 MAP
h104cap cmd "LOG USRCONFIG"    # PROFILE(工作模式) / URFR(安装方向) / COORD(世界坐标系)
```

**为什么先做这个**：如果模块**答了**，就直接排除了"PA10 上不是 H104"这条可能，
并且立刻知道它在用什么波特率、什么帧、什么频率 —— `H104-帧格式规格.md` §7.2 的假设 (b) 当场解决。
如果模块**一个字都不答**（TX 不通 / 它不是 H104 / 它被配成只发不收），那本身就是极强的证据。

命令与应答格式见手册 §ASCII 命令速查表（第 611–655 行）、§查询命令（第 274–284 行）。
发命令前最好先 `LOG DISABLE` 暂停数据输出（手册第 620、257 行），否则应答会被数据帧刷屏。

## 4. 方案 A0：用现成 `serial_test`（只改一行配置）

`serial_test` 在 PX4 里自带、支持 `-R raw` **把收到的字节 hex dump 到 console**、`-e` 打印 TIOCGICOUNT 错误计数：

```sh
serial_test -p /dev/ttyS0 -b 115200 -t -R raw -i 1 -e
#   -t 不发  -R raw 收啥打啥(hex)  -i 1 收 1 秒  -e 打错误计数
```

本板 `default.px4board` **没有**开它 ⇒ 加一行再编译：

```
CONFIG_SYSTEMCMDS_SERIAL_TEST=y
```

**优点**：不用写新代码，`TIOCGICOUNT` 给的 `frame/overrun/buf_overrun` 比 SWD 轮询统计可信得多
（`frame` 高 ⇒ 波特率不对；`buf_overrun` 高 ⇒ 我们读太慢）。
**缺点**：hex dump 走 console。⚠️ **`-i` 只认整数秒**（源码里是 `strtol`，`-i 0.2` 会被读成 `0`），
所以最短就是 `-i 1` ⇒ 约 8200 字节数据 ⇒ hex 文本约 25 KB，**console 环形缓冲装不下，只能看到尾巴**。
**但尾巴够用**：完整帧只要 ~1 KB，尾巴里必然包含若干完整帧 —— 足以回答"是不是 `5A A5` 开头的规整帧"。
若 console 缓冲太小导致尾部是半帧，用 `checklog.sh` **连续多读几次**即可拼上看。

（A0 只能定性；要"字节数一个不差"的证据仍然走 A1。）

## 6. 成功判据（拿回数据后，怎么算"验过了"）

对 dump 出来的 `h104-cap.bin` 跑：

```bash
python3 work/spi-runtime/h104/h104_parse.py -f h104-cap.bin --stats
python3 work/spi-runtime/h104/h104_parse.py -f h104-cap.bin            # 打印前几帧明细
```

| 判据 | 期望 | 若不符 ⇒ 说明 |
|---|---|---|
| `sof_5aa5_count` | ≈ 帧数（约 `n_bytes/82`） | 0 ⇒ **PA10 上不是 HI91 流**（假设 b） |
| `frames_crc_bad` | **0** | >0 且大量 ⇒ 波特率/字节序不对，或帧起点错位 |
| `frames_hi91` | ≈ `n_bytes/82` | 明显少 ⇒ 有丢字节（NuttX 驱动还在丢？查 `buf_overrun`） |
| `odr_hz_est`（按 `system_time`） | **≈ 100 Hz**（出厂默认） | 别的值 ⇒ 模块被改过配置 |
| 静止时 `acc_b` 模长 | **≈ 1.0 G** | 差很多 ⇒ 单位不是 G（或不是 HI91） |
| 静止时 `gyr_b` | **≈ 0 deg/s**，噪声几十 mg / 零点几 dps | 差很多 ⇒ 单位/量纲不对 |
| `main_status` bit7 `ATT_CONV` | 收敛后为 0 | 长期为 1 ⇒ 姿态没收敛（正常，静止 3~5 s 会好） |

**量纲自检的原理**：手册说 HI91 加速度单位是 **G**，静止时三轴合成必然是 1 g 左右 ——
这是一个**不依赖任何外部参考、只靠物理**的强判据；若合成是 ~9.8，说明我们读到的其实像 m/s²（即那可能是 HI83）。
（对照：板载 BMI270 的 1.7 倍增益之谜，就是这么用"静止 = 1 g"抓出来的。）

## 7. 如果拿回来还是"17% 的 0x5A、没有 5A A5"怎么办

那说明**不是抓取方法的问题，而是假设 (b) 成立**，按顺序查：

1. `h104cap cmd "LOG VERSION"` 有没有应答 ⇒ 有 ⇒ 模块在，问题在协议/配置；
2. `h104cap cmd "LOG COMCONFIG"` 看 `BAUD=` 与 `ONTIME=` ⇒ 波特率是不是真 115200、HI91 是不是真的开着；
3. `h104cap cmd "LOG ENABLE"`（或 `LOG HI91 ONTIME 0.01`）把 HI91 明确打开成 100 Hz，再抓一次；
4. 仍然不对 ⇒ **核对原理图：PA10 到底接的是不是 H104 的 TX**（注意网表标注是 `USART1 RX/TX(only AS)`，那个 "AS" 是个没解释的限定词）；
5. 已知 `CAN 在我们固件里完全没开`（`CONFIG_CAN is not set`），如果最终确认 H104 的**主用接口是 CAN1**，那 USART1 只是备口 ⇒ 要么切 CAN（先开 `CONFIG_CAN`+`FDCAN1`，样板 `src/drivers/tattu_can`），要么用 `h104cap cmd "SERIALCONFIG ..."` 把备口配起来。
