## 1. ★ 实验结果：**驱动原时序在芯片上手工重放，100% 成功**

```
0) 初始:            7D=0E 40=8C 41=01 42=A9 43=00     ← 驱动跑完的状态
1) PWR_CTRL=0 后读: 7D=00 42=00                       ← 关断时 0x42 读回 0x00（不是 0xA9！）
2) 写 0x42=CC（关断中，立即读）: 42=CC
3) PWR_CTRL=0x0E +10ms:  7D=0E 42=CC     <<< 驱动就是停在这一步读到 A9
A) 写完 GYR_CONF 后加 1ms:    42=CC
B) 写完 GYR_CONF 后加 5ms:    42=CC
C) PWR_CTRL=0 后等 20ms:      42=CC
D) 先开 PWR_CTRL 再写 GYR_CONF: 42=CC
```

**⇒ 全部 KEEP。**

**⇒ 假说「关断中写 GYR_CONF，被随后的 PWR_CTRL 使能吃掉」—— 否证。**
**⇒ 假说「芯片判定 0xCC 非法、异步回落到缺省 0xA9」—— 否证**（变体 D 在使能后写也存住）。

## 2. ★★ 更强的一条：手工写进去之后，**驱动跑着也抹不掉它**

实验把芯片留在 `42=CC`（变体 D 的残留），`resume` 让 PX4 继续跑，隔几分钟后再读：

```
NOW: 01=69 7D=0E 40=8C 41=01 42=CC 43=00 0B=07
```

| 读到的 | 含义 |
|---|---|
| `42=CC` | **芯片不拒绝 0xCC；驱动也不会把它回落成 0xA9** |
| `0B=07` | DRDY_ACC=1 / DRDY_GYR=1 / DRDY_TMP=1 ⇒ **陀螺确实在转换** |
| `7D=0E / 40=8C / 41=01 / 43=00` | 驱动写过的其余寄存器都到位 |

**⇒ 排除掉"写了又被改回"和"器件拒绝该值"两条之后，只剩一个解释：**

> **驱动对 0x42 的这一次 SPI 写，根本没有落到器件上。**
> 而同一趟 `Configure()` 里对 `0x7D / 0x40 / 0x41` 的写**都落到了**。

## 3. 新线索（记下来，先不展开）

### 3.1 `WHO_AM_I(0x01)` 读回 **`0x69`**，手册缺省是 `0x6A`

只差 **bit0**。而 `probe()` 是靠 `WHO_AM_I == 0x6A` 才认下这颗芯片的 —— 说明**开机那次读对了**，
这次读错了一位。同一路径也出现过 `0x42 = 0xff` / `0x43 = 0xff` / `0x40 = 0xa6`。

**⇒ 单比特级别的读不稳，值得单独排查**（`SPI_SPEED = 10 MHz` 是否偏快 / 采样相位）。
**但它解释不了** `0x42` 每次都能**稳定**读回 `0xA9` —— 稳定 ≠ 随机比特错。

### 3.2 关断时 `0x42` 读回 `0x00`（不是缺省 `0xA9`）

第 1 步实测：`PWR_CTRL=0x00` 之后 `0x42 = 0x00`。
**⇒ 手册里"缺省 0xA9"是"上电缺省"，不是"关断时读回值"。**
含义：驱动在关断中做 `读-改-写`，`orig` 拿到的是 `0x00`（而不是 `0xA9`），
`(0x00 & ~0xFF) | 0xCC = 0xCC` —— 这一步在**数值上是对的**，但值得在仪表里确认。

### 6.5 ⚠️ 残留疑问（诚实记录，不掩盖）

既然 ST-Link 手工重放「关断中写 GYR_CONF 再使能」**也能存住**（§1），
那为什么加了「其它配置写完之后补写一手」就解决了？

目前最合理的解释（**尚未证实**）：
驱动 `RegisterWrite(PWR_CTRL, 0x00)` 之后**只等 1 ms** 就写 `GYR_CONF`，
器件此时可能还没到"接受 GYR_CONF 写"的状态；而 ST-Link 脚本每一步之间有 TCL 往返 + 回读，
**实际间隔远大于 1 ms** ⇒ 手工能成、驱动不能成。

**可验证的下一步**：把 §5.39 那一步的 `1 ms` 改成 `10 ms`（或 `20 ms`），
并把 4b 补写去掉，看单靠"关断中写"能不能立住 —— 若能，说明就是时序余量问题。

> **⇒ 这一条决定 §4 表格里"补写那一手"是"必须的修复"还是"只是兜底"。在证实之前，两处都保留。**

## 7. ⚠️ 顺手挖出来的一个真坑：**手工拉 CS 时 `CR1` 必须是 `0x1201`，不是 `0x1001`**

### 7.1 现象

接手后第一次用自己写的 `chipstate-safe.tcl` 去读芯片 —— **全是 0x00**：

```
SPI1 CR1=00001001 SR=00001002
WHO_AM_I(0x01)=00   0x0B=00  0x40=00  0x41=00  0x42=00  0x43=00  0x7D=00
```

这**看起来就是** `结论文档-器件身份与锁死真相.md` 里描述的"芯片锁死"。
但那份文档同一节又说"CR1 应为 `0x1001`" —— 我照做了，于是**自己造出了这个现象**。

### 7.2 A/B 判决（`cri-ab.tcl`，只改 `CR1` 一个变量）

```
CR1=00001001  ->  WHO_AM_I=00  0x7D=00  0x0B=00  0x40=00  0x42=00
CR1=00001201  ->  WHO_AM_I=6A  0x7D=0E  0x0B=07  0x40=8C  0x42=CC     ✅ 全部正确
```

**⇒ 芯片一直是好的；是读路径不对。**

### 7.3 原因

| 谁 | `CR1` | 为什么 |
|---|---|---|
| **固件**（PC4/PE4 交给 SPI 外设） | `0x1001` | `SSM=0`，NSS 由外设驱动，**读写正常** |
| **手工 GPIO 拉 CS**（本目录所有 `*.tcl`） | **`0x1201`** | 必须 `SSM=1` + `SSI=1`；否则 SSI 被忽略、外设抢 NSS ⇒ **帧错位 ⇒ 全 `0x00`** |

两者差的 **bit9 = SSM**。

**⇒ 修正两条既有文档**：
1. `结论文档-器件身份与锁死真相.md` §2 的"`CR1` 应为 `0x1001`"是**固件侧**的说法 ——
   **拿它去做手工 CS 读会读出全 0，从而误判成"芯片锁死"**。手工路径用 `0x1201`。
2. 老脚本（`chipstate.tcl` / `gyrconf-*.tcl`）用 `0x1201` 是**对的**，不该按上面那条去"修"。

**⇒ 结论：`chipstate-safe.tcl` 现已改用 `0x1201`，并把这段判据写进脚本头注释。**

### 7.4 修正后的复验（同一块板，同一时刻）

```
WHO_AM_I(0x01) = 6A   (与手册缺省一致)
0x0B DATA_STAT = 07   DRDY_ACC=1 DRDY_GYR=1 DRDY_TMP=1
0x40 ACC_CONF  = 8C   0x41 ACC_RANGE = 01
0x42 GYR_CONF  = CC   0x43 GYR_RANGE = 00   0x7D PWR_CTRL = 0E
```

**⇒ 7 个寄存器全对，`0x42=0xCC` 稳住。**
