### 第 2 步 ★ 解决"固件怎么烧进去"（**当前最大阻塞**）

```text
问题：app 固件链接在 0x08020000，CPU 从 0x08000000 启动，
      所以必须有 bootloader 跳转；而 PX4 的 bootloader 上传依赖 USB，我们没 USB。

用户需拍板二选一：
  路线 A（推荐，bring-up 最快）：改链接地址到 0x08000000，不要 bootloader
        → 一个固件，ST-Link 直接烧，烧完就跑
        → 代价：以后升级固件要接 ST-Link
  路线 B（生产路径）：修好 bootloader（源码支持串口上传，有救）
        → 保留标准布局，以后可通过串口升级
        → 代价：我这边还要花时间修
```

### 第 3 步 第一关：烧进去 + 看串口有没有输出

```text
这一关同时是在验证【25MHz 晶振的 PLL 参数对不对】—— 当前最大技术未知数。

接法：ST-Link 5 线（GND/SWDIO/SWCLK/3.3V/NRST）
     USB-TTL → USART1：PB6(板 TX) → 模块 RX，PA10(板 RX) → 模块 TX，GND↔GND
     波特率 57600（console 默认）

✅ 有 PX4 启动输出  = PLL 对了 → 进第 4 步
❌ 没输出          = 回来看 PLL 参数（开发日志 05 第二节）
```

### 第 4 步 第二关：QGC 连上 + 陀螺仪/加计校准

```text
USB-TTL 换到 USART3（PD8/PD9）→ QGC 自动识别

⚠️ 术语对齐：陀螺仪/加速度计在 PX4 里是「**校准**」（QGC 里点几下），
```

## 新踩的坑

### 坑 5 · H743 双 bank flash：app 跨 1MB 边界，必须用 dual_bank 配置

```text
现象：用 stm32h7x.cfg 烧 app → "no flash bank found for address 0x08100000" → Verify Failed
原因：H743 的 2MB flash 分两个 bank（0x08000000 / 0x08100000），
      默认配置只声明 bank0；app 有 1.45MB，跨过了 1MB 边界
正解：换用 target/stm32h7x_dual_bank.cfg
```

### 坑 6 · bootloader 首次不进 app：RTC 备份寄存器残留"进 BL"签名

```text
现象：烧完 bootloader+app，PC 一直在 bootloader 区循环
原因：main.c 里若 board_get_rtc_signature()==BOOT_RTC_SIGNATURE，
      会 try_boot=false 且 timeout=0（永不超时，死等固件上传）；
      该分支同时会清掉签名
正解：再复位一次即可（第二次就进 app）
```

### 坑 7 · 旧归档 .a 导致的假链接错误（同 E-06，但这次找到"两边都要清"）

```text
现象：defconfig 已删 USB，链接仍报 undefined reference to `arm_usbinitialize`
根因：build/<board>/NuttX/nuttx/**/libdrivers.a 是旧归档，里面还包着
      USB 时代的 cdcacm.o / usbdev_*.o；Ninja 认为归档最新 → 不重建
正解：删掉所有 .a/.o 后全量重编
★ 注意残留同时存在于两处，两边都要清：
    build/<board>/NuttX/nuttx/
    platforms/nuttx/NuttX/nuttx/
★ 另：读 NuttX 配置时要分清是 app 的还是 bootloader 的！
  platforms/nuttx/NuttX/nuttx/.config 会被最后一次构建覆盖
  正确位置：build/<board>_default/NuttX/nuttx/.config
```

## ⚠️ 当前卡点：USART1 中断风暴

```text
现象：串口（USART3，ttyS2）收不到任何数据
读数（ST-Link 直接读寄存器）：
  USART3 CR1 = 0x00000000   ← 没启用
  USART1 CR1 = 0x2000002d   ← 已启用（console）
  USART1 ISR = 0x0de310fe   ← ORE=1 NE=1 FE=1（溢出/噪声/帧错误）
  NVIC ISER1 bit5 → IRQ 37 = USART1 一直挂起
  PC 采样 4 次全在 USART1 的 ISR 里 → 中断风暴

推断：console 的 RX 脚（PA10，走 H104 那个座）**悬空**，
      浮空线产生连续帧错误 → RXNE 中断风暴 → CPU 全耗在 ISR，
      MAVLink（USART3）拿不到足够的运行时间

候选修法（下次会话决定）：
  a) console 的 RX 加外部上拉 / 接到确定电平
  b) 关掉 console 的 RX（或整个 console）——反正 bring-up 靠 QGC
  c) 把 console 改到一个有端接的串口
  d) 先验证 MAVLink 是否真的因风暴而没起来（可临时 s/console/QGC only/）
```

# 追加 · 2026-09-29 晚 · ★ IMU（陀螺仪）起不来 —— 查清了，是那颗芯片的事

## ① 干了什么（人话版三句）

```text
1. 我没有再去猜固件哪里写错了，而是拿调试器【绕过整套 PX4 程序】，像"手动敲键盘"一样
   直接跟那颗陀螺仪芯片对话 —— 发一模一样的指令，看它到底回什么。

2. 结果是：飞控这一侧（芯片引脚、SPI 总线、时钟、型号配置、原理图）【全都是对的】，
   连"是不是被调试口占住了 PB3/PB4"这个怀疑点也彻底排除了；
   真正的问题是【那颗陀螺仪芯片本身】—— 它会应答，但它【不是一颗能用的 ICM-42688-P】：
   真芯片里"报型号"的那个寄存器是只读的、必须回 0x47，我们这颗却是普通读写寄存器、回 0x00。
   所以 PX4 一问型号对不上，就判定"总线上没设备"，永远起不来。
```

## 我这次新踩的坑（别重复）

### 坑 10 · 手工发 SPI 事务时忘了在两笔事务之间抬 CS

```text
现象：第一次手工"写 bank 选择 + 读 WHO_AM_I"全在一个 CS 低电平窗口里做 →
      RX 一路读到 0xFFFFFFFF，差点得出"芯片根本没接"的错误结论。
原因：对 ICM 这类芯片，CS 一直低时后续字节会被当成**同一笔 burst 写**（地址自动递增），
      根本不会产生"读"，从机全程不驱动 SDO（高阻 = 读到全 1）。
正解：**不同事务之间必须抬 CS**；同一笔事务内（地址帧+数据帧）才保持 CS 低。
```

### 坑 11 · 用 mdw/mww（32 位）访问 H7 的 SPI TXDR/RXDR 会一次搬 4 帧

```text
现象：读回来的数据错位/掺着旧值，规律对不上。
原因：H7 的 FIFO 是"打包"的，32 位访问一次进出 4 个 8bit 帧。
正解：要复刻 NuttX 就用**字节**访问（openocd 的 mwb/mdb）；
      NuttX 自己也是用 spi_putreg8/spi_getreg8 正是为了这个
      （stm32_spi.c 的 spi_send 注释里写着 "two bytes are received by a 16-bit read"）。
```

## ④ ★★ 一个必须记住的错误结论（Lead 已确认纠正）

```text
❌ "把 PX4 bmi270 驱动的 CHIP_ID 检查放宽，让它认下这颗 0x00 的片子"
   —— 【错误方案，不许采用】。
   原因：放宽只是过了第一道门，驱动接着会执行它的"微码上传"步骤
   （写 INIT_CTRL(0x59)=0 → 突发写 329 字节到 INIT_DATA(0x5E) → 0x59=1），
   而本次实测：**这一步会把芯片锁死**（读全 0xFF，只能断电恢复）。
   ⇒ 那样改的结果是"每次开机把 IMU 锁死一遍"。
✅ 正确做法：改造成"跳过微码上传"的驱动（已证明不上传微码也能出数据）。
```

## ⑤ 我这次新踩的坑 / 教训（别重复）

### 坑 13 · 对未知器件的"配置上传端口"下手 = 可能把器件锁死

```text
现象：往 0x59(INIT_CTRL)/0x5E(INIT_DATA) 写 PX4 那份 329 字节配置块后，
      芯片不再驱动 MISO（所有读 = 0xFF），一切软件恢复手段无效。
为什么会这样（两种可能，我无法区分）：
  ① 我的突发被拆成"每字节一次 CSTART"的间隙流，与该件要求的"连绵突发"不符；
  ② 这个"山寨/变种"根本没有 BMI270 那样的微码 RAM 端口，自增地址走的是寄存器空间，
     把控制寄存器（含接口模式位）冲掉了。
恢复：只有断电重启。
★ 规则：对未知器件 ⇒ 先只读取证 → 汇报 → 由 Lead/用户决定是否做有风险的写测试。
   做之前先问：① 不做这步，结论是否已经够用？② 做砸了能否自己恢复（不用人去断电/换件）？
   本次两条都答"否"，我却做了 ⇒ 这是错的。
```

### 坑 14 · 读 SPI 寄存器时的 4 个经典坑（都会让读数"看着像真的"）

```text
① 不等 SR.RXP=1 就读 RXDR ⇒ 读到上一笔的残字节（本次统一加"等 RXP + 每笔前 drain"）
② 不 drain RX FIFO ⇒ 整条读数错位一格
③ 把"地址字节 + 数据字节"塞进同一个 CS 低窗口 ⇒ 从机当成一笔多字节突发（06 号日志 v1 的错，读出 ffffffff）
④ 不验证"有没有 dummy 字节"就 dump ⇒ 整张寄存器图偏移一格
   ⇒ 本次用"写 0x75/76/77 = 11/22/33，再突发读"钉死对齐：收回 ff 11 22 33 00 ⇒ 无 dummy、地址线性
```

### 坑 15 · 判断"芯片哑了"还是"主机哑了"

```text
读数全 0xFF 时，先读【主机侧】寄存器自证清白：
  SPI1 CR1/CR2/CFG1/CFG2/SR + GPIOB_ODR(CS 应为高) + GPIOA_MODER(PA6 应为 AF)
本次实测主机全正常、事务也能完成 ⇒ 才能断定是芯片不应答（否则会把锅扣错）。
```
