# 上板实测（2026-09-30 晚）：配置回读 3/4 不通过 + 器件停在"常量帧"

> 板载固件 = PX4 `h104-protocol @ 7846181`（驱动仍是旧的 `bmi270` 兼容补丁）
> 实验：`bmi270 stop` → `bmi270 -s -b 1 -R 0 start` → `listener sensor_accel` → `perf` ×2

---

## 1. ★ 校正：`perf` 计数器**会**随模块析构释放

`bmi270 stop` 之后 `duplicate sample` 从 **4,032,597 → 19,046**（重新 start 后从 0 重新累计）。
⇒ 推理：`perf` 计数器在模块析构时释放、重新 start 时重新分配。
⇒ **必须看增量，不能看绝对值。**（这条同时给了我们一个干净的计时起点。）

## 2. `stop/start` **没有救活**器件 —— 一帧之后永久冻结，两次一模一样

两次 `perf` 的间隔用 `mavlink: tx run interval` 推算（507893 → 512186，@100 Hz）：

```
间隔 ≈ 4293 / 100 = 42.93 s
duplicate sample 增量 = 61977 − 19046 = 42931
42931 / 42.93 s = 1000.7 Hz
```

**⇒ 1000 Hz 轮询下每一拍都被判为重复 ⇒ 器件依旧不产新数据。**

反推轮询起点：`5113.4 − 61.98 = 5051.4 s`；
**唯一那一帧发布在 `t = 5060.99 s` ⇒ 轮询开始后 9.6 s。**

⇒ 前 9.6 s 读到的都是**全 0**（`_last_data` 初值也是全 0 ⇒ 判为重复、不发布）
⇒ 第 9.6 s 读到一帧**非 0** ⇒ 发布一次
⇒ 之后恒等于该值 ⇒ 永远重复

### 2.1 ★★ 最狠的一条：那一帧是**常量**

| | 上一轮（旧对象） | 本轮（全新对象） |
|---|---|---|
| x | −0.23379 | −0.23379 |
| y | −0.18620 | −0.18620 |
| z | −9.61424 | −9.61424 |

**小数点后 5 位完全相同**，跨 4000+ 秒、跨一次 `stop/start`、跨一个全新驱动对象。
**⇒ 这不是"又测了一次 1g"（噪声会改变 LSB），这是器件寄存器里焊着的一个常量。**

## 3. ★★ 新发现：**4 个周期性回读检查里约 3 个不通过**

```
bad register: 15 → 47    增量 32
32 / 42.93 s = 0.745 /s  ≈ 3/4
```

（该检查每秒查 1 个，`idx = 1 + (_checked_register % 4)`，4 个轮换：
`PWR_CTRL(0x7D)` / `ACC_CONF(0x40)` / `GYR_CONF(0x42)` / `ACC_RANGE(0x41)`）

上一轮同一比例是 `3024 / 4038 = 0.749`。**⇒ 配置寄存器绝大多数没有读回到目标值。**

**按 `RegisterCheck` 语义（set_bits 必须全置、clear_bits 必须全清）逐个核对：**

| 寄存器 | set_bits | 期望读回 | 实测（独立 ST-Link dump） | 判定 |
|---|---|---|---|---|
| `PWR_CTRL(0x7D)` | 0x0E | 0x0E | 0x0E | ✅ 通过 |
| `ACC_CONF(0x40)` | 0x2C（clear 0x03） | `(X & 0x2C)==0x2C` 且 `(X&3)==0` | 0xAC | ✅ 通过 |
| `ACC_RANGE(0x41)` | 0x01（clear 0x02） | 0x01 | 0x01 | ✅ 通过 |
| `GYR_CONF(0x42)` | 0xEC（含 B6 `GYR_NOISE_PERF`） | 0xEC | **0xA9（缺省值！B6=0）** | ❌ 失败 |

**⇒ 按静态值算只该有 1/4 失败，实测却是 3/4。⇒ 说明还有两个寄存器也不对。**

## 4. ★ 头号嫌疑：单字节读写的**地址对齐**

现有的 `transfer()` 无-dummy 补丁是为**批量读数据寄存器**（14 字节突发）设计的，
注释原话：**「线上返回 13 字节(0x0C..0x18)，transfer() 补丁整体右移一格后 data[0..11] 才是 0x0C..0x17」**。

**⇒ 若单字节 `RegisterRead()` 也走了这条"整体右移一格"的路径，它读到的就是 `addr − 1` 的内容。**

用这个假说验算（假设写入到位、读取错位一格）：

| 检查项 | 实际会读到的地址 | 内容 | 判定 |
|---|---|---|---|
| `PWR_CTRL(0x7D)` | `0x7C`（**不是寄存器**） | 实测返回 `0x03` | ❌ |
| `ACC_CONF(0x40)` | `0x3F` | 未知 | ❌（大概率） |
| `GYR_CONF(0x42)` | `0x41` = ACC_RANGE | `0x01` | ❌ |
| `ACC_RANGE(0x41)` | `0x40` = ACC_CONF | `0xAC` | ❌ |

⇒ 与"绝大多数失败"高度吻合。

**并且它还顺带解释了另外两件事：**
- **`DATA_STAT(0x0B)` 读到 `0x00`** —— 若错位，实际读的是 `0x0A DATA_SAT`，返回 0x00 很正常
  ⇒ **"DRDY 全 0" 这个结论可能是假的，不能据此断定器件停转换！**
- **`temperature: nan`** —— `UpdateTemperature()` 除以 512 后得到 `0x8000` 哨兵，也与错位读法自洽

**⚠️ 反证（不能忽略）**：`probe()` 用 `WHO_AM_I(0x01)` 拿到了 `0x6A` 并成功识别，
如果读操作整体错位一格，读 `0x01` 应得到 `0x00` 而不是 `0x6A`。
⇒ **所以"加一个偏移"不是全局成立的，必须实测确认**：
逐地址读 `0x00 / 0x01 / 0x02 / 0x40 / 0x41 / 0x42 / 0x43 / 0x7D / 0x7C`，看能否自洽。

## 5. 下一步（小、关键、便宜）

**让驱动能看见真实回读值。** 旧驱动只打一句 `last DATA_STAT(0x0B)=0x00`，看不到任何配置寄存器。
新驱动（`hxy42688p`）必须在**启动日志**和 `status` 里逐个打印：

```
0x01 WHO_AM_I    0x05 COM_CFG    0x0B DATA_STAT
0x40 ACC_CONF    0x41 ACC_RANGE  0x42 GYR_CONF   0x43 GYR_RANGE   0x7D PWR_CTRL
```

**这一步同时判决两件事**：是"我们写不进去"，还是"我们读错地址"。
