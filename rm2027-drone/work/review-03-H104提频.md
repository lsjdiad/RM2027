# 第 0 部分 · 结论一句话

> **H104（HI04M0）的规格上限：UART 输出帧率最高 1000 Hz，对应波特率 921600 bps（也是波特率上限）；本板现在跑 100 Hz @ 115200，正好卡在 115200 对 HI91 的带宽天花板上。**
> **提到 200 Hz 只需"模块升 230400 + `LOG HI91 ONTIME 0.005`"两处（驱动同步改波特率）；要到 500 Hz 需 460800/921600；到 1000 Hz 技术上可行（HI91 占 921600 带宽的 89%，手册附表就是这么标的），但因为 `IMU_INTEG_RATE` 缺省只有 200 Hz、`IMU_GYRO_RATEMAX` 缺省 400 Hz，不提这两个参数的话 1000 Hz 对飞控**没有任何收益**。**
> **另外：本模块的真实信息带宽只有 80~200 Hz（HI04MX），所以"提频"买到的是"更小的采样龄抖动 + 不欠采样"，不是"更快的传感器"。**

## 1.2 问题 2：`SERIALCONFIG` 的 10 个波特率档（最高档是多少）

- 手册原文：**「`<BAUD>` 共 10 档：`4800` `9600` `19200` `38400` `57600` `115200` `230400` `256000` `460800` `921600`」** —— `HIP2:228`
- 规格书原文：UART 波特率 最小 **9600** / 典型 **115200** / 最大 **921600** bps —— `HI04:721`
- ⇒ **最高档 = 921600 bps**（手册与规格书一致）。**这就是 H104 提频的绝对天花板**：1000 Hz 输出只能在 921600 上跑。

## 1.3 问题 3：1000 Hz 输出下，数据是"真新采"还是"被 80~200 Hz 带宽滤过的相关样本"

**证据链（全部来自规格书）：**
1. 内部采样率 = **1000 Hz**（陀螺 `HI04:515`、加计 `HI04:601`）⇒ 每个 1 ms 确实有一次新的 A/D 采样。
2. 但 3 dB 带宽：本模块（HI04M0 = **HI04MX**，`HI04:200`）陀螺 **80~200 Hz**（`HI04:511`）、加计 **90~200 Hz**（`HI04:598`）；
   默认 6-DoF 模式更是只有 **80/90 Hz**（`HI04:551`、`HI04:639`）。
3. ⇒ **数据是"每毫秒新采一次，但被 80~200 Hz 低通滤波过的"**，相邻样本高度相关。**不是独立样本。**

**这对"提频有没有意义"的三个直接影响（这才是答案的核心）：**

| 影响 | 说明 | 判断 |
|---|---|---|
| ① 100 Hz 输出对 80 Hz 带宽信号是**欠采样** | Nyquist = 50 Hz < 80 Hz（3 dB 点）⇒ 50~200 Hz 的残余噪声会**折叠**回带内。1000 Hz 输出彻底消除这种混叠 | ✅ **100 Hz→≥200 Hz 有真实收益** |
| ② 输出率降低"样本龄"抖动 | 100 Hz：一帧最多 10 ms 旧；1000 Hz：最多 1 ms 旧。对 1 kHz 内环的定时抖动有意义 | ✅ 有收益，但**只在内环真的跑 >200 Hz 时才体现** |
| ③ 带宽不会变 | 相位滞后由 80 Hz 模拟滤波决定（一阶近似群延迟 ≈ `1/(2π·80)` ≈ **2 ms**），**提输出率一点都改不了** | ❌ **无收益**：H104 不会因此变成"快"IMU |

⚠️ 补充：模块自报的"低输出延时"（`HI04:20`）**没有给具体数字**，所以 2 ms 是我按 80 Hz 一阶带宽估的**量级**，不是手册值；
要精确测必须上板做阶跃/正弦扫频（本报告不臆造该数字）。

## 1.4 问题 4：CAN 上限（200 Hz）为什么比 UART（1000 Hz）低，以及本板走哪条路

**先更正 Lead 的预设：本板根本没有 CAN。**
- 规格书表 3：**`HI04M0-MI0`  UART = 1 路、CAN = ×** —— `HI04:209`
- 表 2：`HI04M0-MI0` 有加计 √、陀螺 √、**磁力计 ×** —— `HI04:203`（与本项目实测 `KF_EN_MAG=0`、`mag_b == 0` 完全吻合，正好互证）
- ⇒ **本板走的是唯一那路 UART**（`/dev/ttyS0` = USART1），表 16 的 CAN 行（`HI04:725`）对本站**不适用**。

CAN 200 Hz 与 UART 1000 Hz 的差异，手册层面**没有写明原因**（表 16 只给数值）。能给出的**可复核**解释只有两条：
1. J1939 周期推荐值里**最小是 5 ms = 200 Hz**（`HIP2:1239`）—— 与表 16 的 200 Hz 上限一致；
2. CANopen TPDO 的示例周期是 10 ms = 100 Hz（`HIP2` CANopen 章），也未低于 5 ms。
⇒ 即"CAN 侧的周期输出在固件里就以 5 ms 为下限"，但**这是数值/示例层面的旁证，不是手册的因果说明**。
（想拿到真正原因只能问厂商；对本项目无影响——我们没有 CAN。）

## 2.5 问题 9：提高波特率 / 输出频率的确切命令序列 + 判据

**顺序原则（手册给的理由）：** `SERIALCONFIG` 若目标波特率**载不动当前已配的输出**会返回 `ERR`（`HIP2:239`）；
反过来"先降速率再升波特率"永远安全。所以：**先提波特率 → 再提速率**（因为提升波特率在任何时候都不会违约）。

```text
# ===== 0. 存档（回滚依据）=====
h104cap ask "LOG VERSION"       # PNAME=HI04M0-...   （确认型号）
h104cap ask "LOG COMCONFIG"     # COM=COM1 BAUD=115200 MSG=HI91, ONTIME=10

# ===== 1. 让驱动让开串口（否则驱动会把 ASCII 应答当二进制流吃掉）=====
h104_imu stop

# ===== 2. 静流（避免应答被 100 Hz 数据帧刷屏）=====
h104cap ask "LOG DISABLE"        # 只是临时停发，不改周期配置（HIP2:258）

# ===== 3. 提高波特率（/dev/ttyS0 = 模块 COM1；HI04M0 只有 1 路 UART，所以省略 <COM>）=====
h104cap ask "SERIALCONFIG 230400"        # 模块在【旧波特率】回 OK，然后立即切换（HIP2:235）
h104cap ask -b 230400 "LOG COMCONFIG"    # 期望 BAUD=230400（HIP2:236）

# ===== 4. 设目标速率（ONTIME 单位是【秒】，读回是【毫秒】）=====
h104cap ask -b 230400 "LOG HI91 ONTIME 0.005"   # 200 Hz
# 目标 500 Hz 时： h104cap ask -b 921600 "LOG HI91 ONTIME 0.002"
# 目标 1000 Hz 时：h104cap ask -b 921600 "LOG HI91 ONTIME 0.001"

# ===== 5. 保存 + 读回确认 =====
h104cap ask -b 230400 "SAVECONFIG"              # HIP2:195,236
h104cap ask -b 230400 "LOG COMCONFIG"           # 期望 ONTIME=5 （毫秒）
#     读回正确 ≠ 已生效（HIP2:199）⇒ 建议再做一次 REBOOT 后复读

# ===== 6. 驱动改波特率后重编、烧写（Lead 负责）=====
# ===== 7. 起来后验收 =====
h104_imu start
h104_imu status     # 期望：发布帧率 ≈ 设定值；CRC坏=0；重同步跳字节不随时间线性增长
perf                # 看 h104_imu 的计数（注意 _perf_overflow 目前恒 0，见 D3）

# ===== 回滚（任何一步失败都可用）=====
h104cap ask "LOG DISABLE"
h104cap ask -b <当前波特率> "SERIALCONFIG 115200"
h104cap ask -b 115200 "LOG HI91 ONTIME 0.01"
h104cap ask -b 115200 "SAVECONFIG"
```

**"超出带宽会被拒绝或丢帧"的三个判据（写死）：**

| 现象 | 判据 | 处置 |
|---|---|---|
| 命令被拒 | `SERIALCONFIG` / `LOG ... ONTIME` 的应答里出现 **`ERR`**（对照 `HIP2:641` 的错误表：`ERROR: Unsupported baud` + `ERR`） | 先降速率 → 再升波特率 |
| 实际丢帧 | `h104_imu status` 的 `CRC坏 > 0` 或 `重同步跳字节` 在 60 s 内增长 > 100 | 降速率或升波特率 |
| 串口溢出 | `resync` 增长 + 帧率低于设定值（`_perf_overflow` 目前无统计，见 D3） | 提 RX 缓冲 / 缩短读取周期 |

# 第 3 部分 · C：反向核查（问题 10~11）

## 3.1 问题 10：不改波特率也能提高有效信息量的路子 —— **HI83 + `MAP` 裁剪**

**依据**：HI83 固定头 8 字节（`HIP2:762-768`）+ 按 `data_bitmap` 选段（`HIP2:770-786`），整帧 = **6 + 8 + Σ段**；
手册自己的对照可以验算：默认 `MAP=0x000000FF` ⇒ 12+12+12+12+16+8+8+4 = 84，+8 头 = 92 数据域，+6 = **98 字节** ——
与手册写的"约 98 字节（数据域 92 + 6）"**完全吻合**（`HIP2:1413`）⇒ 公式可信。

| `MAP` | 段 | 数据域 | **整帧** | 115200 理论上限 | 230400 | 460800 | 921600 |
|---|---|---|---|---|---|---|---|
| `0x001` | acc | 20 | **26 B** | 443 Hz | 886 | 1772 | 3545 |
| **`0x003`** | **acc+gyr** | 32 | **38 B** | **303 Hz** | 606 | 1212 | 2425 |
| `0x007` | +mag | 44 | 50 B | 230 Hz | 461 | 922 | 1843 |
| `0x01F` | +rpy+quat | 76 | 78 B | 148 Hz | 295 | 590 | 1181 |
| `0x0FF`（默认） | +sys_time+utc+baro | 92 | 98 B | 118 Hz | 235 | 470 | 940 |
| — | **HI91（现用，对照）** | 76 | **82 B** | 141 Hz | 281 | 562 | 1124 |

**⇒ 结论：`MAP = 0x00000003`（只留加速度 + 角速度）的 HI83 帧只有 38 字节，比 HI91 的 82 字节短 54%：**

| 目标 | HI91 需要 | **HI83 `MAP=0x03` 需要** |
|---|---|---|
| 200 Hz | 230400（71%） | **115200（66%）—— 不用动波特率！** |
| 250 Hz | 460800（44%） | 230400（82%，偏紧） |
| 500 Hz | 921600（44%） | 460800（41%） |
| 1000 Hz | 921600（89%） | **921600（41%）** |

**代价（必须一起做，否则等于白改）：**
1. **单位不同**：HI83 是 **m/s² 与 rad/s**，HI91 是 **G 与 deg/s**（`HIP2:754`「HI91 的角速度单位是 deg/s、加速度单位是 G；HI83 分别是 rad/s 和 m/s²」；`HIP2:711` 另有一处「相差 57.3 倍」）⇒ 驱动换算必须换系数（差 9.80665 与 57.3 倍）；
2. **必须变长解析**：手册明确要求"解析器必须按每帧头部的 `data_bitmap` 逐段累加偏移，不要依赖固定帧长"（`HIP2:760`、`:273`）；
3. **切换顺序**：先 `LOG HI91 ONTIME 0` 关掉原周期帧，再开 HI83（`HIP2:255`）；COM1 启用 SOUT 时只能有一种周期帧（`HIP2:453`）；
4. **MAP 是全局设置，且要 `SAVECONFIG` + `REBOOT` 才可靠**（`HIP2:273`），改完要检查每帧的 `data_bitmap`；
5. 驱动目前**只认 HI91**（`h104_protocol.hpp:207`：`plen == 76 && tag == 0x91`）⇒ 需要新增 HI83 解析路径。

## 3.2 问题 11：收益 vs 代价

| 维度 | 100 Hz（现状） | 200 Hz | 500 Hz | 1000 Hz |
|---|---|---|---|---|
| 串口负载（HI91 @对应波特率） | 8200/11520 = **71%** | 16400/23040 = **71%** | 41000/92160 = **44%** | 82000/92160 = **89%** ⚠️ |
| H104 侧 RX 缓冲余量（600 B） | 73 ms | 37 ms | 15 ms | **7.3 ms** ⚠️ |
| 驱动读循环占用（128 kB/s 上限） | 6% | 13% | 32% | **64%** |
| uORB 发布量（imu#1） | 200 msg/s | 400 | 1000 | 2000 |
| EKF2 实际积分率 | 200 Hz（`IMU_INTEG_RATE`） | 200 Hz（已是缺省上限） | 需提到 250/400 | 需提到 1000 |
| 内环实际速率 | 由主导 gyro + `IMU_GYRO_RATEMAX`(400) 决定 | 同 | 同 | 需提 `IMU_GYRO_RATEMAX` |
| 信息带宽 | 80~200 Hz | 同 | 同 | 同 |
| 风险 | 现状 `crc bad: 0` ✅ | 低 | 中（需 921600 + 参数） | 高（89% 带宽 + 7.3 ms 缓冲余量） |

**收益的诚实结论**：
- **100 → 200 Hz 是唯一"纯赚"的一档**：消除对 80 Hz 带宽信号的欠采样，刚好对齐 `IMU_INTEG_RATE` 缺省的 200 Hz，负载不变（71%），只改两处。
- **200 → 500 Hz**：需要 921600，收益主要体现在"给 EKF 的积分更细"和"为将来把 H104 升为主导 gyro 留余地"，**必须同时改 `IMU_INTEG_RATE`**，否则白提。
- **500 → 1000 Hz**：**不建议**。89% 带宽 + 7.3 ms 缓冲余量，而 80~200 Hz 带宽决定了拿不到额外信息；要用就把 HI83 `MAP=0x03` 一起做（921600 上只占 41%）。

# 第 6 部分 · 我的判断：该做哪一档

1. **先做 200 Hz（档 1）**：唯一"纯赚"的一档，两处改动（模块 230400 + 驱动波特率），

3. **若目标是"让 H104 参与姿态/内环更高频"**：先确认它是不是主导 gyro（否则提频只影响 EKF 的第二个 IMU），

4. **不建议上 1000 Hz（HI91）**：89% 带宽 + 7.3 ms 缓冲余量，换不来任何信息带宽。
   若要 1000 Hz，走 **HI83 `MAP=0x00000003`**（38 B ⇒ 921600 上只占 41%），代价是新增变长解析 + 换单位。
